0.7.9 · Hotfix

The build cache was always wrong.

After the first build, yamlink publish stopped detecting changes. Edits, additions, and deletions were all silently ignored — your published output fell behind your vault with no error or warning.

Fixed. If you ran yamlink publish more than once since 0.7.7, run --force once after updating to get a clean rebuild.

What changed

The cache compared a constant to itself.

yamlink publish runs as a fresh process each time. The vault's generation counter always starts at 0. The cache check asked: currentGeneration === lastGeneration — which was always 0 === 0. Always true. Every note permanently "unchanged."

Before 0.7.9
$ yamlink publish --out ./site ✓ 38 notes built # You edit three notes, add one, delete one... $ yamlink publish --out ./site ✗ 0 changed · 38 cached edits not detected — output is stale
The deleted note stays in your output. The new note never appears. The edited notes serve stale content. No warning, no error.
After 0.7.9
$ yamlink publish --out ./site ✓ 38 notes built # You edit three notes, add one, delete one... $ yamlink publish --out ./site ✓ 5 changed · 33 cached · 1 removed per-note content hash — correct
The generation check is removed entirely. The cache now compares each note's content hash, which persists between runs. If the hash changed, the note rebuilds. --force still rewrites everything unconditionally.
How it was found

0.7.9 was caught the same way 0.7.8 was — not in a test, but in real use. Running yamlink publish against the actual yamlink.dev source vault, checking the output, noticing that nothing had rebuilt since the first run even though notes had changed.

The bug had been there since 0.7.7 shipped. Every user who ran yamlink publish more than once during that window has stale output. The fix is one command: yamlink publish --force.

Two hotfixes in one day is not a pattern we want. Both were caught because we ran the commands for real rather than trusting the tests. The tests will get better. I will be better.

— Javier, August 2026
Insights

Hi! If I'm to be 100% honest, 0.7.7 was a "controlled whim". Publishing has been part of the Yamlink roadmap for quite some time, ever since a user asked a question in a GH thread. It was not part of the "inception", but the user's suggestion made a lot of sense given what Yamlink was at that point, and what I wanted it to be.

A couple of weeks ago I started working on yamlink.dev manually. As you might imagine, using Yamlink in a real experience made it clear: "I should really get on this now". The gaps were real. No native build command. status: was a label, not a gate. No way to preview against the actual destination. No ordering primitive. Those were the main issues that the website experience forced into existence.

After that came 0.7.8, and now 0.7.9. A crash in yamlink --version. Then the cache bug. I stumbled onto both — not by testing, but by running commands against the site itself.

I put together this "release briefing" because from now on I want to do this for every release. I want it to be a chance to "vent" — for better or worse, in failure or success. And if you enjoy reading, then it's a win-win! I believe in this project. In my heart, I'd want nothing more than for this to be something I can build a career on, and all my free-time work has been pointed toward this. I think I'm onto something here — a platform that only gets smarter the more you use it, completely local, in constant development, adaptable to users' own organic usage trends, and with a lot of plans for a bright future (fingers crossed). The time invested in yamlink.dev is my way of expressing how committed I am to Yamlink as an engine — wherever it goes.

So here's to hoping I get to write a ton more of these!

Cheers,
—j
