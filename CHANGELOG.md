## 0.8.0

### Added

- **Block-ID revision pass, complete: in-editor affordances, block backlinks as a real editor action, and a genuine body-target action.** Previously the only way to know a heading, task, quote, or footnote was block-referenceable at all was to already know the feature existed and run a command from the palette — nothing in the editor showed it. A CodeLens now appears directly above every addressable block: "Copy [section/task/quote/footnote] reference" (one click, no QuickPick needed when the block is already obvious from where the CodeLens sits), and — when another note actually links to that specific block — "N references," which jumps straight to the single referencing note and line, or offers a picker when there's more than one. Reuses the same block extraction (`core/bodyBlocks.js`) and block-backlinks logic (`entityHubModel.js`'s `buildBlockBacklinks`, live since 0.7.6/Sugar) already powering the Note Report panel and CLI/API `block-backlinks` — no new backlink computation, just a new, more discoverable surface for it. **A real body-target action shipped too**: "Extract to note" (`Yamlink: Extract Block to New Note`, also a CodeLens on every task/quote/footnote) moves that exact block out of the current note into a brand-new one, replacing it in place with an `![[embed]]` and setting `source: [[original]]` on the new note — modeled directly on the existing "Split Note Body" command's convention rather than inventing a second one. New `src/features/blockAffordances.js` and additions to `src/actions/blockReferenceCommands.js`, 13 new tests total. This closes the item: precision-reference pickers turned out to already be satisfied by the existing picker's default fuzzy type-to-filter (no new work needed), and "higher-order body-aware surfaces" — a phrase that never had a concrete spec across 3+ sessions — was formally cut rather than carried forward as permanent vague scope.

- **Workflow memory v1 — Yamlink starts noticing which fields you tend to fill in together.** After accepting a completion, if the vault's existing arc-based suggestion has nothing confident to offer, Yamlink now checks whether *you* have a real, repeated pattern of adding two fields together on notes of this type — e.g. always adding `phone` shortly after `email` on `contact` notes. Sessions are detected from real authoring activity (field edits on the same note within a 15-minute window, not a fragile `sessionId` — checked directly and found VS Code never sets one), gated by the same confidence bar already used elsewhere in the codebase (60%+ co-occurrence, at least 2 real sessions) so a one-off coincidence never becomes a nudge. The existing, already-trusted arc-based suggestion always wins when both have something to say — this only fills a gap, never competes with it. Inspect the raw patterns directly with `yamlink workflow-memory --type <type>`. Pure logic in `src/intelligence/workflowMemory.js`, unit-tested directly, plus real tests proving both the fallback-only-when-arc-is-silent rule and the arc-always-wins rule.

- **`yamlink signature` — a real, honest structural signature for the whole vault.** Answers "what shape is this vault, structurally" from the vault's own behavior, not a hardcoded list of archetypes ("this is a CRM vault"). Reports: dominant types (whichever types, taken in order, cumulatively cover 80% of typed notes — not a fixed top-N), field-bundle rigidity per dominant type (0–1, how consistently notes of that type actually share the same fields, reusing `vaultPriors.js`'s already-cached `typeFieldBundles`), hub concentration (what share of all inbound links point at the most-linked-to slice of notes), and recent growth rate (real `note_created` events in the last 30 days as a share of vault size). Every number ships with one plain sentence describing what was actually observed — e.g. "Dominated by `contact` (70%), with a consistent, repeatable field shape (rigidity 0.85), a small number of hub notes carry most of the links..." — never a forced label. Built entirely on data already computed elsewhere (vaultPriors, the graph, the mutation log) — no new vault scan. `--json` supported. Pure computation lives in `src/intelligence/structuralSignature.js`, unit-tested directly (16 tests) plus a real CLI integration test against the sample vault.

- **`yamlink on --daemon` — automation that survives closing the terminal.** Previously `yamlink on <event> -- <script>` only ran as long as its own terminal window stayed open; closing it, or a reboot, silently stopped the automation with no warning. `--daemon` spawns it as a real detached background process instead — `yamlink on field_changed --daemon -- ./sync.sh` starts it, prints its id/pid/log file path, and returns immediately; the actual watcher keeps running after the terminal closes. `yamlink on --list` shows every registered daemon with real, live PID-checked status (a dead one is reported once, then cleaned up automatically). `yamlink on --stop <id>` / `--stop-all` shuts one down or all of them. Output that used to print straight to the terminal now goes to a real log file per daemon (`.yamlink/hooks/<id>.log`) since a detached process has no terminal to print to. Separately, the watcher itself is now retry-and-backoff resilient — a real `fs.watch` failure (platform-dependent, e.g. a flaky network filesystem) used to silently kill the watcher forever with zero indication anything had gone wrong; it now retries up to 5 times with exponential backoff before giving up for good and exiting non-zero with a clear error. **`--daemon` now also recovers from the worker process itself dying**, not just a live process's watcher failing — a lightweight supervisor spawns the real worker as its own child and respawns it with backoff (capped at 5 attempts, so a worker that crashes immediately every time can't loop forever) on any exit that wasn't a deliberate `--stop`. Caught a real, serious bug building this, only via an actual `--daemon` smoke test, not by any unit test: the worker process inherits its parent's environment by default, so without explicitly stripping the internal supervisor flag before spawning it, the worker would re-enter supervisor mode itself and spawn its own "worker" doing the same — an unbounded chain, not a bounded respawn loop. A real run of that bug produced over 1,400 live processes in under a minute before it was caught and killed. Fixed and covered by a dedicated regression test proving the flag never reaches the worker's environment.

- **Smart Templates: missing fields can now pre-fill with a real value, not just a blank line — plus multiple templates per type, a follow-up nudge, and a noise cap.** "Add missing template fields" previously inserted every missing field as a bare `field:` stub. It now checks the same adaptive-suggestion engine behind lightbulb suggestions and completion (`buildFrontmatterOpportunityModel`) for each missing field, and pre-fills it with a real value when the vault has strong, consistent evidence — e.g. a `commander:` field on a `mission` note pre-fills `commander: [[johnny-rico]]` when every other mission in the vault already points there, instead of leaving you to type it. Only ever uses an already-confidence-gated real target — never a half-written `field: [[` placeholder when the vault isn't sure. Fields with no vault evidence still insert blank, exactly as before. The confirmation message now says which fields were pre-filled versus left blank. **Multiple templates can now exist for the same type** — `_templates/<type>.md` still works exactly as before when there's exactly one, but "Save as Template" now offers to overwrite an existing one or save a new, distinctly-named template, and "Add missing fields" asks which template to use when more than one matches; template-drift detection deliberately stays silent for a type with more than one template rather than guessing which one applies. **Auto-insertion is capped at 6 fields per run** — a template with more missing fields inserts the first 6 and says how many more are available, instead of dumping everything into the note at once. **A separate, optional follow-up nudge** appears after insertion when the vault has one more genuinely relevant suggestion beyond the template's own fields (a real "Insert" action, not applied automatically). Pure logic (`selectSmartFieldInsertions` in `src/actions/nodeCreationTemplates.js`) is unit-tested directly against a real built vault, not mocked.

- **Multi-note authoring — one field change across many notes, now from all four surfaces: CLI, API, VS Code, and Conduit.** Previously changing a field on several notes at once meant one `yamlink set` invocation per note. `yamlink bulk-set --ids <id1,id2,...> --field <name> (--value <v> | --add <v> | --clear)` applies it to every listed note in one call: `--value` overwrites the field, `--add` treats it as a wikilink-list relation (creates the list if the field doesn't exist, skips silently if the exact link is already present — running it twice never creates a duplicate — and fails clearly rather than guessing if the field already holds a plain scalar value), `--clear` removes it. A bad id or an incompatible field in the batch fails only that note; the rest of the batch still completes, and the command exits non-zero only if at least one note failed. `--dry-run` and `--json` both supported. **`PATCH /api/nodes/bulk` supports the same `--add` semantics** — pass `{ add: "value" }` instead of a plain value for a field to get identical add/idempotency/scalar-failure behavior over the API, sharing the exact same logic with the CLI (`src/core/bulkFieldOperation.js`) rather than a second, parallel implementation. **VS Code: select multiple notes in the Explorer, right-click, "Yamlink: Bulk Set Field on Selected Notes"** — same Set/Add/Clear choices, same per-note failure isolation, applied via the same cheap incremental per-file index update every other VS Code write command already uses. **Conduit: the Explorer's existing multi-select bulk-action menu gained a 4th option, "Add to list field"** — alongside the set-field/set-status/delete actions already there, reusing the same field-name/value input flow and the same `PATCH /api/nodes/bulk` `{ add }` semantics as everywhere else, not a separate implementation. Still explicit-selection only by design across every surface — no query/filter-based selection anywhere (`--ids` or an explicit note/file selection only). Fixed a related, real gap while building the CLI piece: `yamlink set` (the single-note command) wrote directly to disk and never went through `vaultService.mutate()`, unlike every other CLI write command (`create`, `rename`) — harmless in practice since `yamlink set` only ever runs as a one-shot process that exits right after, but a real deviation from the project's own write-path convention. Fixed to match.

- **`GET /api/graph/history`** and `yamlink graph --since/--until/--points` — a real checkpoint series over a time range, not just the existing single-point-in-time `?at=` graph. Built on the Time Engine reconstruction primitives already shipped in 0.7.4 (`reconstructVaultAtTime()`, `buildHistoricalGraph()`) — this is new surfacing, not new reconstruction logic. Supports either a fixed `points` count (evenly stepped between `since`/`until`) or a real interval (`Nm`/`Nh`/`Nd`/`Nw`), capped at 50 checkpoints per request. Originally built as the data source for a planned Conduit timeline scrubber — that UI was built and then removed the same cycle (see `ROADMAP.md`'s struck-through entry), but this endpoint/CLI surface stands on its own regardless.

- **Vault dependency preview — "what if I delete this."** Deleting or renaming a note that other notes still depend on no longer fails silently after the fact:
  - `DELETE /api/nodes/:id` now returns `409 DEPENDENCIES_PRESENT` with the real reference count and breakdown (frontmatter relations vs. body mentions) unless `?force=true` or an `X-Yamlink-Force` header is sent.
  - `yamlink rename` shows the real linked-reference count up front and, when run from a real interactive terminal, asks for confirmation before renaming a note with linked references — `--force` skips the prompt. A non-interactive caller (a script, CI, or any other caller with no terminal to prompt) proceeds automatically, since `rename` is documented as an unconditional vault-wide operation and most real notes have at least one inbound reference; the dependency count is still shown in the output either way. `--dry-run` stays non-blocking so it can always be used to check first.
  - Conduit's Explorer delete flow (single and bulk) now shows the real dependency count in a clean message instead of raw JSON, and offers a genuine force-confirm step (`y` to force delete anyway, `n`/Esc to cancel) rather than just reporting the block and stopping — you can actually resolve it from Conduit now, not just from the CLI or API.
  - Note Report gained an always-available **Dependencies** tab (`src/features/entity/entityHubSections.js`) showing the same data outside of any delete/rename action — which notes reference this one, split by frontmatter field vs. body mention, with real counts. Reuses existing backlink data (`getBacklinks()`) throughout — no new intelligence primitive.

- **Live inline unlinked-mention highlighting.** A note's name/id/aliases appearing as plain text elsewhere in the vault — without a formal `[[wikilink]]` — is now underlined live as you type, not just discoverable by opening Note Report's "unlinked mentions" list. A quick fix (`Yamlink: Link mention to [[id]]`) turns it into a real link on the spot, preserving the original wording as a display alias (`[[johnny-rico|Johnny Rico]]`) when it differs from the canonical id, with a second option to normalize to the bare `[[id]]` form. Built on a new generation-cached vault-wide term index (`getUnlinkedMentionTermIndex()` in `src/features/entity/unlinkedRefs.js`) reusing the exact same `buildSearchTerms()` logic Note Report's existing detection already uses, so the two can never disagree — ambiguous terms shared by two or more notes are dropped from the index entirely rather than guessed at. Measured at 6.66ms against a 10ms live-decoration budget on a 66,610-character note with 4 indexed terms.

- **VQL v1: graph traversal and temporal reconstruction in `!view` queries.** `!view * linked_to [[id]]` returns every note with an outbound edge to `id`; `!view * linked_from [[id]]` returns every note `id` itself points to. An optional `within N` (e.g. `linked_from [[id]] within 2`) extends either clause transitively — the union of everything reachable in that direction across 1 to N hops, not just exactly hop N. Capped at 5 hops; an out-of-range value degrades to a plain single hop with a parse warning rather than erroring. Cycle-safe (a real graph has real cycles — traversal tracks visited ids so it can't loop or double-count). Omitting `within` behaves exactly as the original single-hop release did — same result, same query string on round-trip. Built entirely on the graph primitives already used elsewhere (`getBacklinks()`/`getEdges()` in `core/graph.js`) — no new graph algorithm, just a small BFS layered on top, resolved once per query into a plain id `Set` rather than per-row, so it costs no more than any other `where` filter. Composes with type filters and other `where` clauses (`!view unit linked_from [[mission-klendathu]] within 2`), and multiple traversal clauses intersect (AND) rather than union. **`as of <date>` reconstructs a query's results as of a past point in time** — `!view mission as of 2297-08-10 where outcome = ongoing` runs the whole query (type filter, `where`, `select`, `sort`) against each note's frontmatter as it stood on that date, not today. Accepts the same date vocabulary `where` clauses already do (a literal date or `today()`/`days-ago(N)`/etc.). No new reconstruction logic — this is new surfacing of the existing Time Engine primitive (`reconstructVaultAtTime()`, already powering `cat --at`/`graph --at`/`GET /api/graph?at=`). A stated limitation: computed/virtual fields (`_inbound_count`, `file.created`, etc.) are not reconstructed and still reflect current values; doesn't apply to `!view incoming` at all (separate code path). It does combine with `linked_to`/`linked_from`, but not into a true point-in-time traversal — the traversal itself always walks today's live graph edges, and `as of` only reconstructs the field values shown for whichever notes that live traversal already selected (verified directly, not assumed — corrected 2026-08-20 after this bullet originally overstated the restriction). An invalid `as of` date degrades to a warning and current-state results rather than erroring.

- **Conduit: layered glass contexts.** Navigating deeper (Explorer → a note → Graph centered on it, for example) now pushes the screen you came from onto a real context stack instead of discarding it. A thin strip at the screen's edge shows the trail you've taken (capped at 4 levels), and Esc peels back through it one level at a time instead of always bouncing to a fixed home screen.

- **Webhook registration API.** `GET/POST /api/hooks`, `PATCH/DELETE /api/hooks/:id`, and `yamlink hooks add/list/remove` register a URL to receive a real HTTP `POST` whenever a specific mutation event happens in the vault (any of the ~26 known mutation event types, optionally scoped to one note type). Delivery is best-effort — a failed delivery is logged, never blocks the vault write or rebuild that triggered it. Backed by `.yamlink/webhooks.json` per vault; a real dispatcher runs inside `yamlink serve`'s own rebuild cycle, no separate process required (unlike `yamlink on`, which needs a terminal left open).

- **LSP: real adaptive-frontmatter suggestions on the `type:` line, not a stripped-down copy of VS Code's.** Placing the cursor on a note's `type:` line once it has a value now offers real, vault-pattern-derived code actions — e.g. "add likely context (unit → roughnecks)" or "add smart setup (add name, unit, rank)" — built from the same shared, already-portable suggestion engine LSP's own completion already uses, not a duplicate. The presentation is genuinely LSP-native rather than a port of VS Code's `viewLightbulb.js`: short, individually-titled actions instead of one narrative bundle, and a single, unambiguous trigger (the `type:` line itself) instead of VS Code's broader blank-line-anywhere-in-frontmatter behavior.

- **Importer trust profiles — a real "what to expect" summary before and after every vault import.** Previously an import confirmation screen only showed structural counts (files, links, conflicts) with no signal about how faithfully that specific export format can actually be rebuilt. A new shared profile (`src/importers/importTrust.js`) states, per platform, what comes over well, what needs a quick review, and what the export format itself makes impossible to fully rebuild — e.g. Notion's exports don't carry enough data for Yamlink to reconstruct real relations, rollups, formulas, or views, no matter how the importer is written. A one-line version now appears in the VS Code import confirmation QuickPick (Obsidian, Notion, Evernote, Roam all wired), and a longer "What to expect from this import" section is added to every generated import report. 1 new regression test covering all three trust profiles, plus new assertions in the existing Notion report test.

### QOL

- **x-graph: dragging a node now pulls its connected neighbors along, live.** Previously a drag only ever relocated the one node — the layout engine settled once when the graph first loaded and then sat fully static, with nothing left running for a drag to feed into. Dragging now briefly reheats the physics engine and runs it live for the duration of the drag (and for a moment after release, until it re-settles), so connected notes visibly respond via the same spring forces that shape the graph on load — closer to Obsidian's live graph feel. Applies to both the Graph Workspace panel and the sidebar mini-graph; landed entirely inside the shared `graphPhysicsEngine.js` engine, so both surfaces picked it up automatically with no changes to either panel's own code.
- **x-graph: "Hover Focus" toggle, off by default.** Previously, hovering *or* dragging a node always dimmed everything not connected to it — which meant dragging a node around the graph plunged the rest of it into darkness for the whole gesture. Off by default now: hovering and dragging no longer dim the rest of the graph, so nodes can be repositioned freely while staying oriented in the full picture. Turn it back on (Graph Workspace toolbar, and the sidebar mini-graph's compact "Focus" button) to restore the old hover-dims-the-rest behavior. An explicit click-to-select still always dims the rest regardless of the toggle — that's a deliberate action, not an incidental side effect of hovering past a node while dragging another one.
- **Bulk "link all" quick fix for repeated unlinked mentions.** The mention-linking quick fix above previously required one click per occurrence — a note mentioned three times unlinked in the same document meant three separate fixes. When the same target appears more than once in a document, a second quick fix now offers "Link all N mentions of [[id]] in this note" alongside the single-mention one, applying the same alias-preservation rule to every occurrence at once.
- **The bundled sample vault now demonstrates computed fields and Vault Glossary, not just the guided-tour prose describing them.** `sample/` is what a new user opens first, and had zero notes actually exercising `_inbound_count`/`_outbound_count`/`_hub_score` (Computed Fields, shipped 0.7.5) or Vault Glossary (also 0.7.5) — both real, working features with nothing in the demo vault showing them off. Added a "Most Connected Notes" `!view` block to `query-shortcuts.md` sorted by `_hub_score`, and real `definition:` fields to two `dossier` notes plus a short guided-tour section in `note-report.md` so `Yamlink: Open Vault Glossary` has real entries the moment you try it.
- **Live Note preview: less noise, real task progress, more of the note is actually click-to-source.** Empty frontmatter fields no longer render as pills — a blank `gender:` previously showed as a "gender · empty" pill with the same visual weight as `id`/`type`. Metric chips now omit zero-value metrics instead of showing a bare "0", and the tasks metric shows a real done/total ratio (`2/5`) instead of a meaningless raw count. Task checklist items are now click-to-source, jumping straight back to that line in the editor, and show a real checked/unchecked visual state — previously only headings, `!view` blocks, and frontmatter pills could do this; the actual body content had no source mapping at all. Identity pills and metric pills now carry real visual hierarchy (metrics visibly quieter) instead of sharing near-identical styling with only an accent-color difference.
- **Removed leftover dev-session scratch text from `sample/johnny-rico.md`.** The vault's flagship demo note — the one most likely to be a new user's very first open — had checklist items reading "Let's see how this looks in the report" and "Test #urgent," plus a duplicate sentence and an empty "### Testing" heading with nothing under it, all clearly artifacts of building the sample content rather than real demo material.
- **Note Outline: block-aware branching.** Task and quote blocks now nest under the heading section they physically fall under, instead of the outline tree showing headings only — each reuses the same click-to-navigate behavior headings already have, with a distinct icon per block type. Reuses the block extraction already powering block-level backlinks and `[[note-id^block-id]]` references (`core/bodyBlocks.js`) rather than a second, separate extraction. Footnotes are deliberately not included — they're inline-referenced, not section-scoped, and where they'd nest in a tree like this isn't answered yet.

### Fixed

- **Vault import audit fixes — Obsidian, Notion, Evernote, and Roam.** Following a real audit of all four importers against each tool's actual documented export format (not just our own test fixtures):
  - **Obsidian**: Markdown-style internal links (`[Note](Note.md)`) now rewrite to canonical wikilinks alongside the existing `[[Note]]` handling — Obsidian vaults with wikilinks disabled previously kept plain Markdown links on import. A vault using a custom-named `.obsidian`-equivalent config folder is now detected by its contents (real Obsidian config filenames like `app.json`/`workspace.json`) rather than only the literal folder name, and skipped from import like the standard folder already was.
  - **Notion**: HTML exports (a real, supported Notion export format) are now imported and converted into stamped Yamlink notes — previously only Markdown/CSV exports were accepted. Multi-value CSV cells containing a real comma (e.g. "Acme, Inc.") no longer get incorrectly split into two fake values — only semicolons split multi-value cells now. The original Notion export ID is preserved as a `notion_source_id` field where available, so pages with identical titles don't lose their distinct identity.
  - **Evernote**: `<en-todo>` elements now convert to real Markdown task checkboxes (`- [ ]`/`- [x]`) instead of being silently dropped. `<en-media>` attachment references now resolve to a real link to the extracted attachment file at its actual position in the note, instead of the attachment surviving only in frontmatter with no indication of where it belonged in the body. `<en-crypt>` encrypted sections now become an explicit "[Encrypted Evernote content]" placeholder (with the author's own hint text, if one was set) instead of silently vanishing.
  - **Roam**: block UIDs are now preserved as `^uid` block anchors on each imported line, and `((uid))` block references / `{{embed: ((uid))}}` embeds now resolve into real Yamlink block wikilinks (`[[page-id^uid]]`) pointing at the actual block, instead of surviving as raw, non-functional Roam syntax.
  - 6 new regression tests added across the importer test files (43 total now passing, up from 37).
- **The Command Palette entry for "split note body into a new note, keeping the original as an embed" was mislabeled with a title that actually described a different command.** `yamlink.splitNoteBody`'s real behavior (moves the selection into a new note's body, leaves `![[new-id]]` embedded in place, sets `source: [[original-id]]`) was correct and already matched `GETTING_STARTED.md`'s own description — but `package.json` gave it the title "Yamlink: Extract Selection to New Note," which is what `yamlink.newNoteFromSelection` (a different command — replaces the selection with a plain `[[link]]` instead) actually does. Searching the Command Palette for "Split Note Body" found nothing. Retitled to "Yamlink: Split Note Body" to match its real behavior; `FEATURES.md`/`GLOSSARY.md` corrected to match.
- **`codeActions.js`'s "Create &lt;type&gt;" broken-link quickfix recomputed a vault-wide field-frequency count from scratch on every single render**, manually rescanning the whole `fieldsCache` twice just to show a number in the button label ("Create character (4 fields)") — duplicating exactly what `vaultPriors.js`'s cached, generation-keyed `typeFieldBundles`/`typeBundleTotals` already store. Now reads the existing cached prior instead; same threshold, same displayed count, verified via a new regression test (this quickfix's label had no test coverage at all before).
- **Four more files hit the same bare-`\n`-split + `$`-anchored-capture CRLF bug already fixed once in `bodyBlocks.js`.** On a Windows-line-ending (CRLF) note, splitting body text on a bare `\n` leaves a trailing `\r` on every line; `.` never matches `\r`, so a `$`-anchored capture regex silently matches nothing instead of erroring. Found via a full audit of the pattern across all source/test files (68 had a bare `\n` split; only 4 also had the specific `$`-anchored regex against the same split text, which is the actual bug condition). Fixed in `previewRenderer.js` (footnote definitions and image preprocessing — Live Note preview), `pdf.js` (PDF export body/callout segmentation), and the LSP's `documentStructure.js`/`semanticTokens.js` (frontmatter field parsing, heading detection, semantic token ranges) — all four now split on `\r?\n`, with regression tests proving CRLF- and LF-joined content produce identical output.
- **The sidebar mini x-graph was missing a containment-clamp fix already shipped in the full Graph Workspace panel.** Disconnected or low-weight satellite nodes could drift arbitrarily far off-screen under charge repulsion from the main cluster in the sidebar view specifically — the two panels' force-layout code had quietly drifted out of sync with each other. Fixed by consolidating both onto one real, shared layout engine — see Internal below.
- **A dragged x-graph node could become permanently unclickable.** Dragging a node writes its new position straight into the renderer without rebuilding the click-detection grid, which is only ever rebuilt on a full graph reload — so once a node moved far enough to cross into a different grid cell, nothing could hit-test it again until the graph reloaded. Most noticeable on a disconnected node (nothing nearby ever triggered an incidental refresh to paper over it), but affected any dragged node. Fixed: the hit-test grid now rebuilds the moment a drag ends.
- **Conduit's Navigator screen crashed with "Maximum update depth exceeded" after two Down-arrow presses.** Root cause: two effects were feeding each other — one pushed the cursor's selected note up to the app shell on every cursor move, and the other synced the cursor back down from that same value once the app shell echoed it back as a prop, but the second effect re-ran on *every* cursor move rather than only when the echoed value actually changed, so it kept forcing the cursor back to stale positions. Two rapid key presses landed the two effects out of sync with each other, and the resulting oscillation never converged. Fixed: the echoed value is now only ever applied once, so it can't fight the user's own subsequent navigation.
- **Sorting a `!view` by a computed field put every note with a genuine zero at the wrong end of the sort, mixed in as though it had no value at all.** `_inbound_count`, `_outbound_count`, and `_hub_score` can legitimately be `0` (an isolated note has zero inbound links), but the sort comparator used `value || fallback` — and `0` is falsy in JavaScript, so a real zero silently fell back to the note's id string instead of sorting as the lowest number it actually is. Found while adding the sample-vault computed-fields demo above, which surfaced it immediately on any disconnected note. Fixed to treat a real `0` as `0`.
- **LSP hover, go-to-definition, and workspace-wide diagnostics could answer against a stale, pre-rebuild index right after an edit.** The same race class already fixed once for code completion (`handleCompletion`), never audited in the other three: a watched-file change schedules a debounced rebuild (~300ms) rather than rebuilding synchronously, and the server's message dispatch is fire-and-forget per frame, so a request landing right after an edit could be answered before the rebuild it should reflect had actually finished — a moment where hovering a just-created note's link, jumping to its definition, or running a full-vault diagnostics scan could silently show stale data. Fixed by awaiting the same `vaultService.flushPendingRebuild()` guard `handleCompletion` and pull-diagnostics already used, added to `handleHover`, `handleDefinition`, and `handleWorkspaceDiagnostic` (the pull-diagnostics handler `handleTextDocumentDiagnostic` already had it — only the workspace-wide scan was missing it). 3 new end-to-end regression tests, each independently confirmed to fail without the fix and pass with it — an earlier version of these tests passed regardless of the fix due to unrelated subprocess-startup timing, caught and corrected before being trusted.
